  games=作品机制、apis=全能力开放层（§2.5）

## 2. engine 内部工作原理（v0 主张保留）

- **World + System 管线**：World 是状态容器，System 是可扩展的类
  （呼应"面向对象、可扩展"——system 是基类+子类扩展，不是散函数）；
  每帧执行序 = 一屏可读的管线清单
- **sim 只产事件流**：msgspec tagged union 的 Event，view/api/replay
  全是消费者；输入只走 InputFrame，view→sim 反向通信禁止
- **VM 指令即数据**：ECL/ANM/MSG/STD 全部 decode 成强类型指令对象，
  `{InstrType: handler}` 注册表分派；无 elif 链、无魔数下标、无 -1 哨兵
- **SceneSnapshot 协议**：后端只拿"要画什么"的快照，拿不到 world 本体
- **组合根显式化**：`games/thNN/compose.py` 一个函数拼出完整作品装配

## 2.5 apis 层：全能力开放 + worker 异步（用户定案）

apis 不是"受保护的门面"，是**对修改开放的全能力层**：音频系统、
游戏资源目录、GUI 绘制等引擎全部能力都暴露给调用方，不限制每帧
调用次数，不假设调用方是轻任务。

由此推出三条线程规矩（这层的设计核心）：

- **sim 状态只有主线程能改**：apis 收到的写操作（改世界/播音频/建实体）
  一律落成命令入队，在帧边界统一应用——调用方随便什么时候调，
  模拟的确定性和时序不受影响
- **重任务上 worker**：apis 提供 `submit(fn) -> Future` 把工作提交到
  worker 池异步执行（AI 躲弹、图像处理、批量资源解析这类重活）；
  worker 里只能碰传入的不可变快照，结果经事件流/Future 回主线程
- **读走快照**：apis 的读路径给的是 SceneSnapshot/状态副本，调用方
  拿着随便算，不持有 world 本体——异步安全从结构上保证，不靠
  "调用方自觉别乱摸"

音频/GUI/资源这类系统级服务（不碰 sim 状态的）可以直接同步调用，
worker 规矩只约束碰世界状态的部分。

## 3. lint 与风格红线（用户定案 + 落法）

| 规矩 | 落法 |
|---|---|
| type hint py310+ | ruff `UP` 规则族 + `target-version = "py310"` |
| 导入必须在模块顶部 | ruff `E402` + AST 守护测试（函数内 import 抓 AST） |
| 包内禁止绝对导入自己 | AST 守护测试（ruff 没有"强制相对"的现成规则，
  我们有 AST 守护先例，一条规则的事） |
| 面向对象、可扩展 | 设计约束，不可 lint——system/VM/后端全走基类+注册扩展 |
| docstring Google 风格、不 AI 味 | ruff `D` 规则族（convention=google）+
  规范文档约束（一句话职责，出处单行注释） |
| 禁 Optional，用 `X \| None` | ruff `UP045`（py310+ target 下自动抓） |

以上全部第 0 天配好（pyproject + 守护测试 + CI），先于任何业务代码。
